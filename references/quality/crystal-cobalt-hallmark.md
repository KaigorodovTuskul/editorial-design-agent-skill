# Crystal Cobalt — Hallmark & Production QA Integration

## Goals

Treat Hallmark as a real installed diagnostic rather than a vaguely cited design influence. Maintain visual ambition and financial document-specific quality checks. Honor the chosen blue-violet atmospheric identity without pretending incompatible Hallmark rules pass unchanged.

## Known source-level conflicts

Hallmark v2's `Floor` rules include an explicit ban on purple-to-blue gradients (`2a`), plus UI-specific rules about small labels, density, and heading treatment. Crystal Cobalt intentionally permits blue/violet atmospheric fields; the AEB source uses these prominently in multiple section pages.

**Do not:**
- ignore the failure;
- remove Hallmark's output from logs;
- claim an official clean Hallmark report where its upstream rules rejected a page;
- apply Hallmark's website word-count limits to analytical financial tables.

**Do:**
- pin upstream version/commit;
- run actual upstream source and render checks;
- store raw reports and screenshots;
- run an editorial adapter with an explicit exception ledger;
- enforce layout, legibility, truthfulness and export quality independently;
- label an exception as `APPROVED_STYLE_CONFLICT`, never as an upstream pass.

## Validation sequence

1. **Preflight:** input data, fonts, brand assets, dimensions, deterministic page count, asset origin.
2. **Static:** CSS/HTML parsing, missing classes, font declarations, unresolved fonts/images, clip and overflow checks, text-to-background contrast in rendered positions.
3. **Hallmark:** run upstream checks; save upstream results verbatim. Identify conflicts by clause (do not blanket-waive everything).
4. **First render:** produce a whole-deck contact sheet and full-size samples of all major page families. Main model or independent critic flags issues with page IDs and bounding boxes where possible.
5. **Fix batch:** resolve repeated problems at design-system level; repair page-specific issues in one batch.
6. **Second render:** compare before/after images; inspect changed and previously broken pages. Keep an issue ledger.
7. **Optional third render:** only if unresolved major or newly introduced defects.
8. **Export:** HTML/Chromium PDF + hybrid native-text PPTX, re-render PPTX with target engine; compare original and PPTX. Save report with actual measured metrics, not a boolean based on PPTX structure.
9. **Release decision:** READY only if hard gates pass; if missing Hallmark or fonts, NOT_READY (or explicitly DRAFT with reason).

## LLM cost controls

- At most three visual passes, ordinarily two.
- One deck contact sheet instead of repeatedly sending all full-size pages to the model.
- Full resolution only for pages with high risk (dense charts, long headings, two-up complex layouts) and reported failures.
- One optional fresh-context reviewer/subagent for major deliveries, not one reviewer per page.
- Cache render geometry, font map and screenshot hashes to avoid redundant work.
- Separate mechanical fail from aesthetic critique; don't ask LLM to recalculate data or check CSS syntax.
- Never claim checks ran if prerequisites are absent.

## Hard production gates

1. Wrong/missing fonts or substitution.
2. Broken Russian glyphs or units.
3. Overflow, clipping, accidental collisions or unintelligible microtext.
4. Incorrect chart numbers or sources.
5. Unlicensed or unauthorized corporate marks.
6. Invalid document dimensions or missing pages.
7. PPTX source-vs-render mismatch above explicit acceptance thresholds.
8. Hallmark dependency absent where contract requires it.
9. Screenshots or docs generated by a model claimed as verified facts.

## Human approval

For public investor-facing materials, `READY` denotes mechanical/design readiness. It does not replace legal, accounting or management sign-off on statements and projections.
